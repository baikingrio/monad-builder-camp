# 2026-08-03｜Week 4：OddLane 收敛 ZeroDev 交易账户方案

## 今日目标

今天围绕 OddLane 的交易账户体验做架构收敛：用户首次启用交易账户后，买入、卖出、撤单和领取不应每次都唤起钱包签名，同时不能为了“像 Web2”而把用户私钥交给服务端。

OddLane 的协议主线保持不变：

```text
Prediction-native Fully Onchain CLOB
+ Complete Set
+ Pyth
+ Single-Lane Rollover
```

本次讨论的是提交交易的账户层，不改变订单簿、抵押、Oracle 或结算的链上经济规则。

## 既有账户抽象实践回顾

此前在 Monad Builder Camp 中已经完成过 Safe、ERC-4337 EntryPoint、Counterfactual Account、Sponsored UserOperation 与受限 Session Key 的实践和基础链上检查。

这次重新梳理后，重点不是继续从零实现一套通用智能账户，而是评估能否在 Monad 上复用成熟 AA 基础设施，减少账户、Validator、UserOperation 和 Bundler 接入的重复风险。

## ZeroDev 调研结论

根据 ZeroDev 当前官方文档：

```text
Monad Mainnet（143）和 Monad Testnet（10143）
均在支持网络列表中
```

文档同时提供：

```text
Kernel Smart Account
+ Permission / Session Key
+ Call / Timestamp / Rate Limit / Gas Policy
+ Bundler / Paymaster 项目 RPC
+ Passkey / WebAuthn
```

并将 Monad Testnet 列入 Native Passkey Precompile 网络。

这意味着 OddLane 可以优先站在 ZeroDev Kernel 的基础上实现交易账户，而不是自研通用 ERC-4337 Smart Account。

## 产品决定：一次启用，后续快速交易

交易账户的目标体验收敛为：

```text
Connect Wallet
→ 点击「启用交易账户」
→ 一次明确授权
→ 后续 Buy / Sell / Cancel / Redeem 不反复弹钱包
→ 用户随时可以撤销快速交易
```

用户不需要在开户时配置时长、次数或额度。安全参数应是产品侧的固定、保守预设，并在账户安全页向用户说明，而不是把复杂权限表单变成交易门槛。

## 权限边界

ZeroDev Kernel 将作为用户的 OddLane 链上账户地址，现有订单簿仍按该账户的可用 / 预留现金与 Outcome Balance 记账。

后续 Session Key 的链上权限应收敛为：

```text
允许：Place / Cancel / Redeem
限制：指定 PredictionOrderBook、value = 0、函数白名单、时间窗口、频率与 gas
禁止：Withdraw、Approve、任意外部调用、Pyth / Keeper / Lifecycle 管理
```

针对订单累计金额、订单参数和 OddLane 业务不变量，需要增加专用的 `OddlaneOrderPolicy`，不能只依赖前端提示或 Paymaster 后端策略。

```text
Paymaster 负责 Gas
≠ 替用户授权
≠ 可以放宽 Session Key 权限
```

## 方案收敛

OddLane 的 AA 只保留一条主线：

```text
EOA / Passkey Owner
→ ZeroDev Kernel
→ Permission Validator / Session Key
→ Monad Testnet E2E
→ 有限 Paymaster
```

不再考虑自研通用 Smart Account。若 ZeroDev 的 Bundler、Permission Policy 或真实 Testnet UserOperation 验证未通过，项目保持现有 EOA 交易路径，而不维护第二套账户系统。

下一步按以下 Gate 推进：

```text
ZeroDev Monad Testnet Project / RPC 预检
→ Kernel / EntryPoint / Permission Plugin 版本锁定

```
